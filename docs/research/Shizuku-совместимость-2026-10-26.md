# Shizuku и форки: совместимость AliceBridge 2.0

Проверено 26.10.2026. Это исследование исходников, документации и присланных журналов, а не подтверждение работы на всех перечисленных телефонах. Файл «Шизуку.doc» не использовался.

## Что действительно установлено

Для AliceBridge важны четыре разные проверки: получение Binder и разрешения; запуск нашего UserService; создание сети и передача пакетов; запросы реального клиента хотспота. Надпись «Shizuku запущена» подтверждает только часть первого уровня. Проверка DNS из телефона не заменяет проверку DNS из колонки.

Основной метод остаётся DFRoot. Shizuku предлагается как альтернативный способ. Рекомендация менеджера зависит от Android, процессора, сборки ОС и конкретной ошибки, а не только названия оболочки. До реального теста нельзя писать «этот форк исправляет интернет на HyperOS».

### Самый предметный случай: MediaTek

У upstream есть отдельные сообщения [#1171](https://github.com/RikkaApps/Shizuku/issues/1171) и [#1198](https://github.com/RikkaApps/Shizuku/issues/1198) про UserService. README thedjchi прямо указывает исправление; оно также описано в [релизе r1196](https://github.com/thedjchi/Shizuku/releases/tag/v13.6.0.r1196-thedjchi). Это основание испытывать ветку с исправлением, если менеджер работает, но наш UserService не запускается. Утверждение распространяется на этот тип сбоя, а не на все MediaTek и не на весь HyperOS.

## Требования к реализации v2

1. DFRoot выбран по умолчанию. Резервный способ доступен без сброса сохранённой сессии.
2. Обнаруживать работающий API/Binder, а не только установленный пакет `moe.shizuku.privileged.api`. Пакет нужен для открытия менеджера и объяснения конфликтов.
3. После разрешения запускать минимальный UserService с тайм-аутом; сохранять UID, API/server version, причину bind failure, PID и смерть Binder. Не показывать permission granted как доказательство успешного запуска сервиса.
4. Раздельные результаты: UserService, создание интерфейса, tethering, native engine, физический upstream, DNS UDP/TCP/AAAA с клиента, HTTP/HTTPS с клиента. Недоступный тест имеет статус «не проверено», не «успешно».
5. При Wi-Fi→AP→мобильной сети повторно выбрать физический upstream; не направлять SOCKS обратно в собственный testtun. Отслеживать `onLost`/`onAvailable` и смерть сервиса.
6. Сначала рекомендовать тест на мобильном интернете. Если Wi-Fi и AP могут работать одновременно, этот режим проверять отдельно; не требовать второго телефона для настройки.
7. Если нет Binder — инструкция запуска. Есть Binder, нет UserService на MediaTek — предложить ветку с исправлением. Есть TUN, неправильный DNS — показать сетевую ошибку, не отправлять человека менять менеджер вслепую.
8. Копирование APK с другой подписью не является обновлением поверх. Смену менеджера объяснять; автоматически ничего не удалять, не включать Device Owner и не выдавать дополнительные разрешения для функций форка.
9. В журнал писать фактические данные, не гадать об оболочке. Диагностика: build fingerprint/SDK/patch/SoC, manager package/version/signature, API/server version/UID, способ запуска, Wi-Fi/mobile/VPN/Private DNS, iface/address/routes, реальные результаты клиентских тестов с временем.
10. Данные о форках — справочник, а не автоматический загрузчик APK. В UI показывать ссылку на релизы и статус «требует проверки», пока нет полного теста AliceBridge на такой комбинации.

## Что ещё не проверено на устройствах

Замена менеджера на каждом присланном телефоне; совместимость текущего Shevery с нашим UserService; Porter companion/direct API; полный проход колонки через Next/Plus/Nightzuku; повторное подключение после смены upstream и после перезапуска телефона. README и наличие релиза не закрывают эти проверки.
