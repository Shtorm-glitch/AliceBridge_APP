# AliceBridge 2.0 — техническое задание

Дата: 26 октября 2026. Статус: рабочая спецификация для будущей разработки.

## 1. Цель и границы

Создать Android-приложение заново, используя проверенные наработки AliceBridge,
а не перенося существующий монолит и его глобальное состояние. Основной продукт —
приложение Android и обслуживающий его сервер DNS/прошивок. Веб-панель пользователю
не нужна. Windows/Electron — отдельный возможный проект, не часть этого задания.

Версия 2.0 должна провести пользователя от подготовки телефона до рабочей панели
управления колонкой, объясняя текущий этап, результат, следующий шаг и восстановление
после ошибки. Получение root телефона и root колонки — разные операции и статусы.

Новая реализация сейчас не начинается. Этот документ сохраняет требования и опыт.
Предложения по стеку и спорные протокольные решения согласуются перед разработкой.

Штатный сценарий: один Android-телефон с AliceBridge и «Домом с Алисой».
Пользователь переключается между двумя приложениями на этом же телефоне.
Второй телефон не требуется; инструкция, сетевой сценарий и приёмка не должны
зависеть от его наличия. Хотспот и фоновая сессия AliceBridge продолжают работать
при открытии «Дома с Алисой» и возвращении обратно.

## 2. Зафиксированные продуктовые решения

- Android 12L+ — целевой минимум приложения. Доступность каждого сетевого способа
  проверяется отдельно; работа Shizuku на всём диапазоне версий не предполагается.
- При новом запуске способ не выбран; DFRoot показывается первым. Приложение само запускает получение
  временного root, затем проверяет реальный доступ через su.
- Перед стартом объяснить необходимость менеджера KernelSU и дать ссылки на
  релизы для Samsung и остальных телефонов, без привязки к старому номеру релиза.
- При нескольких менеджерах KSU предложить выбор. После получения root показать:
  открыть «Суперпользователи» и выдать права приложению AliceBridge.
- Временный root телефона исчезает после перезагрузки. После завершения DFRoot
  сессии явно напомнить о необходимой перезагрузке телефона.
- При неудаче DFRoot предложить Shizuku; автоматически другой способ не запускать.
- В инструкции второго способа два понятных варианта: «HyperOS — скачать Shevery»
  и «Другие смартфоны — скачать Shizuku». На главной эту инструкцию не дублировать.
- Для проверки Shizuku рекомендовать мобильный интернет телефона. Объяснить запуск
  службы через беспроводную отладку и возможную потерю службы при смене сети.
- YAM, YSE/Entware, SSH, Zsh и apkg устанавливаются по отдельным кнопкам,
  с подтверждением того, что будет установлено. Автоустановки этих компонентов нет.
- Fastfetch — автоматический дополнительный шаг после обязательной настройки;
  ошибку можно пропустить. Используется fastfetch, не screenfetch.
- YAM имеет отдельные вкладки «Пакеты» и «Плагины». YSE/Entware — отдельный инструмент.
- apkg — проект пользователя initialfox, не подмена на yapkg.

## 3. Пользовательские сценарии

### 3.1 Открытие приложения

Сразу показать доступную кнопку «Начать настройку». Поиск готовых колонок идёт
в фоне и не блокирует старт. Одна подтверждённая колонка с ADB открывает панель;
при нескольких показать выбор: понятное имя, модель, адрес, версия, состояние доступа.
Автоматический поиск не должен менять настройки найденных устройств.

При начале новой настройки пользователь обязан явно выбрать точную модель
колонки. Модель по умолчанию не подставляется. Карточки содержат название, поколение,
изображение корпуса/кнопок и помощь «Где посмотреть модель». Для похожих поколений
показать отличия; у Макс уточнить ревизию. Если пользователь не знает модель,
предложить её определить по наклейке или данным «Дома с Алисой», не угадывать.

Выбор модели заменяет отдельную галочку «У меня Станция 1» в новой версии:
серверный профиль Станции 1 включается выбранной моделью. Выбор сохраняется в сессии,
передаётся backend и участвует во всех нужных запросах, включая allow_update.
Фактическая модель из запросов/ADB сверяется с выбором. При конфликте остановиться
до выдачи неподходящего образа, а не считать выбор пользователя доказательством модели.

После выбора сначала показать отдельный экран сброса именно этой модели.
Кнопка «Колонка сброшена, продолжить» — подтверждение пользователя, а не отметка
автоматической проверки. Показать также «Изменить модель» и «Не получилось сбросить».
На экране сброса объяснить потерю локальных настроек и необходимость новой привязки.
Не обещать, что сброс гарантированно установит конкретную старую прошивку.
Не предлагать подключение к обычной сети до готовности хотспота AliceBridge.

В новом сценарии способ не выбран до нажатия пользователя; инструкция раскрывается после выбора. Галочка «Поддержка WPA1 для
Станции первого поколения» выключена по умолчанию, расположена под выбором способа
и доступна только в DFRoot. Выбор Станции 1 сам по себе WPA1 не включает.

### 3.2 Настройка новой колонки

1. Обязательный выбор точной модели и, где нужно, ревизии.
2. Сначала показать инструкцию сброса выбранной модели; дождаться подтверждения
   пользователя и приветствия колонки. Только затем переходить к настройке телефона.
3. Проверить телефон, способ доступа, интернет и выбранный сервер.
4. Получить/проверить права и разрешение пользователя в менеджере.
5. Поднять хотспот и проверить его реальную конфигурацию и сетевой тракт.
6. Только после успешного старта показать сеть и пароль. Справа у каждого поля —
   значок копирования. Объяснить: открыть «Дом с Алисой» на этом же телефоне,
   добавить/привязать колонку к этой сети и вернуться в AliceBridge.
   Не заставлять заранее доходить до экрана выбора Wi-Fi.
7. Обнаружить колонку, сверить выбранную модель с фактической и получить текущее ПО.
8. Провести OTA-сценарий, если он нужен для выбранного профиля.
9. Дождаться возвращения той же колонки после установки/перезагрузки, учитывая новый IP.
10. Подключить встроенный ADB, проверить устройство и доступ, выполнить профиль модели.
11. Показать каждый обязательный шаг отдельно, затем fastfetch с возможностью пропуска.
12. Предложить дополнительные инструменты по кнопкам и завершение настройки домашнего Wi-Fi.

Для входа в панель уже работающей колонки по ADB сброс не требуется: это другой
сценарий. Обязательный начальный сброс относится к новой настройке/прошивке.

Ошибка Bluetooth в «Доме с Алисой»: понятная подсказка закрыть и заново открыть
именно приложение «Дом с Алисой», затем повторить подключение.

### 3.3 Домашний Wi-Fi

Отдельный полноценный экран. Название сети и пароль текущей сети телефона
подставляются при наличии доступного разрешённого способа чтения. При недоступности —
ручной ввод с объяснением. Не показывать технические строки типа `AB_DATA=...`.
Пароль скрыт; в поле есть глазок. Не путать домашнюю сеть с хотспотом AliceBridge.

Перед переключением проверить готовность обязательных шагов, отсутствие реально
выполняющейся установки и доступность профильного способа смены сети. Завершённый SSH
не должен одновременно считаться ожидающим установки и блокировать переход.
Отдельные адаптеры для Buildroot и Android Станции 1: путь wpa_supplicant нельзя
считать одинаковым на всех моделях.

После команды показывать: колонка меняет сеть, ищем её новый адрес, прошло столько-то
времени. Подключение телефона к домашней сети, остановка хотспота и обнаружение колонки
должны иметь явный порядок для каждого способа; если одновременные STA/AP невозможны,
показать необходимое действие пользователя. Хотспот не выключать слепым таймером.
При долгом поиске дать повторную проверку и инструкцию восстановления сессии.
Перезапуск приложения — запасная мера, а не обязательный штатный шаг.

## 4. Архитектура приложения

Предлагаемый стек: Kotlin, Compose, coroutines/Flow, ViewModel, Room для событий
и восстановления, DataStore для настроек. Утвердить перед началом работ.

Разделить ответственность:

| Компонент | Ответственность |
| --- | --- |
| SessionCoordinator | Единственный владелец состояния и переходов текущей сессии |
| PrivilegeProvider | DFRoot/KSU и Shizuku/Shevery с разными возможностями |
| HotspotController | Поднять, проверить, остановить точку; параметры и клиенты |
| NetworkController | Upstream, DNS UDP/TCP, маршруты, VPN, очистка собственных правил |
| BackendClient | Версия протокола, сессия, модель, прогресс и доступность сервера |
| Discovery | Кандидаты из DNS, DHCP/соседей, предыдущей идентичности и ADB |
| AdbTransport | Один транспорт, явная выбранная колонка, таймауты, reconnect, push, PTY |
| DeviceProfile | Возможности, прошивки, сценарии и ограничения конкретной модели |
| SetupEngine | Отдельные операции с проверкой результата, повтором и сохранением прогресса |
| Tools | YAM, Entware/YSE, apkg, SSH, Zsh, fastfetch |
| Diagnostics | События, сводка, подробный журнал, экспорт и удаление секретов |
| AppUpdater | Проверка версии APK, изменения, загрузка и установка обновления |

UI отображает состояние координатора; UI не запускает параллельно собственные
сетевые циклы. Процесс не хранит единственный источник истины в static Session.
Таймеры, сокеты, процессы и фоновые задачи принадлежат одной сессии и имеют отмену.
Повторный старт, двойное нажатие и возврат Activity не создают второй монитор/прокси.
Остановка идемпотентна. Новые задачи после закрытия executor не допускаются.
Ресурсы освобождаются даже при ошибке очистки маршрутов или su-команды.

## 5. Состояния и доказательства прогресса

Базовая цепочка новой настройки: выбор модели → инструкция сброса и подтверждение →
подготовка телефона → права → проверенный хотспот → колонка обнаружена →
версия/профиль → предложение прошивки → передача → ожидание установки/перезапуска →
ADB → профиль настройки → домашний Wi-Fi → панель.
У каждого шага: ожидание, выполнение, готово, ошибка, отменено, пропущено,
не поддерживается. Пропуск обязательного шага не превращает всю настройку в успешную.

Для каждого результата хранить источник, время, ID сессии/устройства и признаки
актуальности. Предыдущий успешный проход не подтверждает текущий.

- 100% передачи — сервер отправил файл; это не доказательство установки на flash.
- Установка подтверждается новой версией от того же устройства. Перезапуск —
  изменением boot ID, если его удалось прочитать; до ADB он может быть неизвестен.
- Обнаружение по DNS не подтверждает работающий интернет, ADB или root.
- Проверка интернет-доступа телефона не заменяет проверку трафика клиента хотспота.
- Root телефона не означает root колонки; UID adbd и UID root worker показываются отдельно.
- Явное отклонение сертификата после передачи: «Возможно, прошивка не подошла»
  с исходной ошибкой и оговоркой, что установка не подтверждена. Таймаут и отсутствие
  HTTP-запросов не классифицируются как ошибка сертификата.
- Старая версия после полной передачи должна отображаться как «установка не подтверждена /
  колонка продолжает сообщать прежнюю версию», а не бесконечное уверенное ожидание reboot.
- Потеря обратной связи не сбрасывает историю в «колонка ещё не подключалась».
  Сохранённые данные маркируются устаревшими и не используются как новые доказательства.

## 6. Профили моделей и прошивки

Каталог должен различать: распознаётся модель; есть образ; образ проверен;
есть реализация сценария; подтверждён проход на реальном устройстве.
Наличие ZIP на сервере не означает подтверждённую поддержку.

Начальный реестр: Лайт 1 (`yandexmicro`), Мини 1 (`yandexmini`), Мини 2
(`yandexmini_2`), Мини 3 (`bergamot`), Лайт 2 (`plum`), Миди (`cucumber`),
Станция 1 (`yandexstation`), Макс (`yandexstation_2`). Алиасы и ревизии проверять
по устройству и свежим исходникам; не смешивать Макс с Станцией 2 по похожим именам.
Остальные найденные платформы не включать автоматически без отдельного профиля.

Фиксированные известные ориентиры для повторной проверки:

| Профиль | Исходная база для проверки 2.0 |
| --- | --- |
| Лайт 1 | `0.369.1.46.4778262442.20261013.297` |
| Мини 1 | `1.305.4.16.3237824040.20250721` |
| Станция 1 | `2.369.5.46.4778391386.20261013.52` |
| Макс без Zigbee, YNDX-0008 | `5000000921`, build `PPR1.180610.011.5000000921`; экспериментально |

Для остальных моделей выбирать проверенный профиль и согласованную версию.
Для Лайт 2 не считать 21 октября подходящим автоматически: ранее запрошен образ
до 21-го, а при отсутствии — минимальный доступный с зеркала с явным статусом проверки.
Даты хранить абсолютными, а не правилом «21-е текущего месяца». Не выводить
уязвимость только из даты. Текущие выборы сервера вынести в отдельный проверяемый реестр.

Образ проверяется по модели/ревизии, размеру, SHA-256/CRC32 и структуре.
Numeric Android build ID обрабатывается явно, не как дата или Buildroot-версия.
Поддержать докачку Range, реальное объединение диапазонов без двойного подсчёта,
новый прогресс при повторном полном GET и отдельный статус оборванной передачи.

### 6.1 Buildroot-профили

OTA, постоянный ADB и аналитика — отдельные действия с чтением состояния до/после.
Способы и пути для Мини 1, cucumber и Лайт 1 могут различаться.
Если основной способ OTA не сработал, использовать проверенный резервный способ
данного профиля, а не применять общий скрипт к любой файловой системе.
Транспортный таймаут останавливает очередь команд: reconnect и продолжение
незавершённого шага. Завершённое действие повторно не применять без причины.
Порядок закрепить так, чтобы необязательная аналитика не мешала сохранить ADB;
предлагаемый порядок: блокировка OTA → постоянный ADB → аналитика → fastfetch.

### 6.2 Станция 1

До ADB общий сценарий, после — отдельный профиль Android/tulip.
Использовать предоставленный пользователем root boot и сценарий этой модели.
Готовый образ и резервный заводской хранить на сервере с проверяемыми метаданными.
Не требовать совпадения исходного boot с единственным старым заводским хешем,
если выбранная поддерживаемая конфигурация допускает отличия.
При этом обязательны проверки модели, разметки/размера, хеша записываемого образа,
успешности записи и полного readback. Нельзя отключать их общей кнопкой «игнорировать».

Перед записью резервная копия; после записи sync, readback, понятное предупреждение
о перезагрузке, затем проверка boot ID, той же колонки и реального root ADB.
Резервную копию хранить на телефоне до проверки/восстановления. После успеха удалять
лишние staging/boot-файлы на колонке, не занимая место под пакеты.
Отключение OTA, SSH, смена Wi-Fi и root-терминал — профильные, не Lite-скрипты.

### 6.3 Макс

Отдельные ревизии и Android-сборки. Имеющиеся бинарники предназначены для 0921;
инструкция YNDX-00053/0914 не доказывает их совместимость. Нужны свои проверенные
бинарники/параметры и испытание на соответствующем устройстве.

Различать runtime root, Permissive и постоянный доступ. Не обещать постоянный root
без внешнего восстановителя. Cache guard не называть полным отключением OTA.
Одна попытка на boot ID; ограничение переживает смену IP и перезапуск приложения.
Не запускать второй exploit параллельно. После исчерпания попытки — инструкция reboot.
Опциональное восстановление при активной сессии: снова проверить профиль,
поднять root и запустить уже установленный YAM. Сам YAM — только по кнопке.
Учитывать `/data/quazar/yam` и `/data/yam`; использовать nohup и проверку API.
Автономный OpenWrt-восстановитель — отдельная интеграция с проверкой boot ID;
вечный lock-файл на роутере не заменяет отслеживание перезагрузки колонки.

## 7. Сеть и сервер

Весь клиентский DNS UDP/TCP направляется на выбранный сервер, без доменных
списков на телефоне. Приложение не расшифровывает произвольный HTTPS клиента.
Сервер обслуживает необходимые домены/OTA по утверждённому протоколу.
Служебные запросы пропускаются по явной политике; дополнительные запросы в Яндекс
ради проверки приложение само не создаёт. Регистрация — предусмотренное исключение
проксирования. Локальный шаблон sync сохраняется с профильной активацией ADB.

DFRoot и Shizuku используют разные сетевые адаптеры с единым контрактом результата.
Проверки: hotspot interface, адреса/шлюз, upstream, UDP/TCP DNS, A/AAAA,
реальный клиентский трафик, доступность сервера и очистка маршрутов.
WPA1 — опция только DFRoot, выключена по умолчанию; после применения проверять
фактический режим и шифры. Не писать «WPA1 включён» только по успешному вызову API.
Для Станции 1 учитывать 2,4 ГГц, режимы PHY и возможности драйвера телефона.

VPN показывать как отдельный фактор: через что идут телефон и клиенты хотспота,
совпадает ли выход для DNS-обратной связи и HTTP колонки. `NXDOMAIN` или отказ порта
53 не переводить автоматически в диагноз «сервер не поддерживает AliceBridge».
Различать недоступность сервера, перехваченный DNS и несовместимый протокол.

На сервере:

- Отдельные обработчики check_updates, allow_update, register, sync, generate_204,
  OTA и служебного проксирования; общая модель сессии, но не общий catch-all JSON.
- Для allow_update сохранять модель/выбранный образ из однозначного контекста,
  включая ручной выбор Станции 1. Отсутствие platform в этом запросе само по себе
  не является причиной hasUpdate:false. Совпадающая подтверждённая версия — false.
- Не связывать несколько колонок/приложений только по внешнему IP. Явный device ID,
  срок жизни контекста, конфликты модели и NAT учитываются в контракте.
- Надёжную привязку приложения и запросов колонки за NAT/VPN спроектировать отдельно
  и подтвердить экспериментально. Не обещать её на основании одного session token,
  который сама колонка ещё не передаёт. При неоднозначности — явная ошибка.
- Ответы и манифесты совместимы с проверенными исходниками lite-kit и профилем.
  Контрактные тесты сохраняют точные запросы/ответы без пользовательских секретов.
- TLS: проверять ключ/сертификат/цепочку/имя и фактическое доверие нужного клиента
  прошивки. Не менять сертификаты наугад из-за сетевого таймаута.
- Сервис запускается после reboot сервера. Обновления разворачиваются с healthcheck,
  резервной копией и rollback; активные передачи прошивок не обрываются ради рестарта.
- Сервер DNS меняется в настройках приложения. Адреса прошивок, обратной связи,
  образов boot и APK должны иметь понятную единую конфигурацию и правила миграции,
  а не скрытые независимые IP в разных классах.

## 8. Панель, инструменты и терминал

Панель показывает выбранную колонку, модель/buildname, версию, IP, тип root,
доступность ADB/SSH и место по нужным файловым системам. Пустое поле — «не получено»,
а не ноль или подтверждение успеха. Смена выбранной колонки закрывает старые forward/PTY.

YAM: установка, открытие, пакеты/плагины, поиск, установленные/каталог,
импорт .yap, удаление, запуск/остановка и журналы задач. Источники и схемы каталога
версионируются; изменения GitHub API не должны выглядеть как «пустой каталог».
YAM API открывается через ADB-forward на выбранное устройство, а не localhost
самой колонки или старой сессии. Совместимость пакетов проверяется по архитектуре/ОС.

Entware/YSE и необходимые базовые архивы доступны из APK либо проверенного кэша,
с manifest/hash; не зависеть от ненадёжного скачивания bootstrap при каждом запуске.
apkg и fastfetch используют согласованные пути и PATH для Buildroot/Android.

SSH: Dropbear, явные порт/пользователь, пароль по запросу пользователя по умолчанию
`1`, возможность сменить. Проверять бинарник, запуск, API/порт и автозапуск после
настоящего reboot. Большие скрипты передавать файлом, избегая shell command too long.
Чужой процесс с переиспользованным PID не останавливать.

Терминал — отдельный широкий экран с настоящим PTY, интерактивными htop и подобными
программами, изменением размера, клавишами Ctrl/Tab/стрелками. Для Станции 1 — root.
Zsh: установка, PATH, окружение, готовая тема и запуск как пользовательского shell;
применить в текущем терминале сразу. Замена системного shell-файла не является
обязательным способом: точное поведение задаёт профиль и сохраняется путь возврата.

Проблемы места диагностировать по mount/filesystem, свободным байтам и inode.
Показывать staging, кэш, резервные копии и место пакетов отдельно. Не удалять
пользовательские данные и не менять разделы ради ложного ENOSPC.

## 9. Журнал и экспорт

Обычный журнал — понятные события сценария, предупреждения и ошибки. Повторяющиеся
ADB-отказы сворачиваются в одну строку со счётчиком, временем и последней причиной.
Полные команды/вывод/сетевые детали — в раскрываемом техническом режиме и архиве.
Шум не скрывает новую существенную ошибку. Есть фильтр текущей сессии.

Кнопка «Поделиться диагностикой» формирует ZIP и сразу открывает системный Share,
не требует сначала вручную сохранять файл. ZIP включает:

- версию APK/протокола, телефон/Android/способ/разрешения;
- текущую и предыдущую сессии с явными границами и временем;
- идентичность колонки, версии, boot ID, шаги/попытки/подтверждения;
- сетевые интерфейсы, upstream/VPN, маршруты, собственные DNS-правила и тесты;
- события сервера для связанной сессии, включая тела нужных ответов после очистки;
- полный ADB-журнал и результаты проверок, место, процессы установщиков;
- исключения со stack trace, а не только error.getMessage();
- список неполученных разделов и причины (нет прав, таймаут, устройство пропало).

Wi-Fi/SSH-пароли, приватные ключи, токены аккаунтов и серверные credentials
не попадают в архив. Тесты проверяют очистку и в stdout/stderr команд, и в JSON.
Сбор архива не запускает настройку, не меняет сеть и не создаёт новый exploit.

## 10. Обновление приложения и публикация

При каждом открытии проверять обновление. При новой версии — полноценный экран
с версией, списком изменений, «Обновить» и «Пропустить». Пропуск не скрывает
следующее предложение при следующем запуске. Загрузка с прогрессом/повтором,
проверкой размера, SHA-256 и совместимости подписи перед установкой.

Публикация атомарна: сначала APK и проверка прямого скачивания/Range, затем
метаданные OTA. Именованная версия, актуальный alias и историческая публичная
ссылка обновляются согласованно. Не терять ключ подписи между релизами.

Исходники приложения и backend — в отдельных пользовательских GitHub-репозиториях,
с лицензиями/NOTICE, инструкцией сборки и self-hosting. README объясняет настройку
DNS и рекомендует PR для важных доработок. Приватные сертификаты, credentials,
диагностики пользователей, local.properties и рабочие дампы не публикуются.
Документация в wiki/4PDA обновляется по фактической поддержке, без обещаний
непроверенных моделей. PR и назначения ревьюеров — по согласованному процессу.

## 11. Критерии приёмки

1. Быстрые повторные start/stop, уничтожение сервиса и повторный вход не оставляют
   мониторы/сокеты. Нет RejectedExecutionException каждые две секунды и EADDRINUSE
   от собственного старого DNS-прокси.
2. При DFRoot failure доступен осмысленный переход к инструкции Shizuku; mode не
   меняется без выбора. Отсутствие root телефона в Shizuku — ожидаемое состояние.
3. Симулятор на отдельном клиенте проверяет UDP/TCP/AAAA DNS, generate_204,
   check_updates, allow_update, sync и Range/обрыв передачи для каждого профиля.
4. Отдельные тесты: ручная Станция 1, отсутствие модели у allow_update, старая/
   целевая версия, несколько колонок за NAT, устаревший контекст, несовпадение модели.
5. После DHCP/reboot выбирается та же колонка; свежий DNS имеет приоритет над старой
   REACHABLE/PROBE-записью. Чужая колонка по старому IP не получает команды.
6. Транспортный таймаут при настройке не запускает последующие скрипты и OTA fallback
   через оборванный ADB. После reconnect продолжается незавершённый шаг.
7. Установка, перезагрузка, root, постоянный ADB и SSH имеют независимые проверки.
   «Файл передан» не становится автоматически «всё успешно».
8. Смена домашней сети проверена отдельно на Мини 1, Лайт 1 и Станции 1, затем на
   остальных заявляемых профилях. Интерфейс показывает поиск и действия восстановления.
9. YAM, SSH, Entware/YSE, apkg, Zsh не устанавливаются автоматически; есть подтверждение.
   Fastfetch можно пропустить; Zsh работает сразу в текущем терминале.
10. Диагностический архив позволяет восстановить последовательность одной сессии,
    не содержит секретов и остаётся доступным при сбое ADB/root/сети.
11. Новый backend проверяется извне и через приложение, на фактическом адресе его
    DNS-listener, а не на постороннем локальном stub-resolver.
12. Модель попадает в список «проверено» только после воспроизводимого прохода
    на реальном устройстве с сохранённым результатом и точной версией прошивки.

## 12. Последовательность разработки

1. Повторно получить актуальные upstream-репозитории; снять изменения с момента
   наших копий. Зафиксировать commit SHA, лицензии и изменения контрактов.
2. Утвердить матрицу профилей, протокол backend и модель сессии/отмены.
3. Собрать каркас UI и координатор с fake-транспортами; проверить жизненный цикл.
4. Реализовать сеть DFRoot и отдельно Shizuku с внешним симулятором клиента.
5. Подключить серверный контракт OTA/allow_update/feedback и восстановление ADB.
6. Перенести и проверить профиль Лайт 1/Мини 1, затем Станцию 1, остальные и Макс.
7. Подключить домашний Wi-Fi, пакеты, SSH, терминал и диагностику.
8. Пройти реальную матрицу устройств, подготовить миграцию/OTA и выпуск.

Существующий код используется как источник проверенных команд, тестов и регрессий.
Старые глобальные циклы, неявные зависимости и catch-all обработчики не переносятся.
Свежие upstream-изменения не устанавливаются поверх production без сравнения и тестов.

## 14. Накопленные регрессии на дату ТЗ

- Исправление backend allow_update уже развёрнуто 26 октября: галочка Станции 1
  используется при запросе без platform. Проверено на живом сервере: true с выбранной
  прошивкой; false при совпадающей версии. Локально проходят 37 backend-тестов.
- На телефоне владельца пойманы 60 RejectedExecutionException из старого мониторинга
  после завершения executor. Причина должна устраняться жизненным циклом сессии,
  а не только скрытием записей. В рамках подготовки ТЗ этот app-баг не исправлялся.
- В истории того же телефона есть EADDRINUSE при запуске DNS-прокси. Нужны проверка
  единственного владельца порта, отмена предыдущего запуска и cleanup при ошибках.
- Отдельно наблюдались NXDOMAIN, ECONNREFUSED и ENETUNREACH обратной связи. Они не
  являются тем же исключением executor и должны диагностироваться независимо.
- У другого пользователя Станция 1 получала образ, продолжала сообщать старую версию,
  а на телефоне был VPN upstream tun0. Тест: повторные Range, allow_update,
  потеря обратной связи и отсутствие подтверждения установки одновременно.

## 15. Требования из разбора Telegram

Основание: `docs/research/Telegram-AliceBridge-2026-10-26.md`.
Это тематическая выборка прочитанных веток, не полный разбор всех сообщений/вложений.

- Проверять уже существующий root до запуска DFRoot. KernelSU, KernelSU Next,
  установленный менеджер, разрешение и фактический UID su — разные признаки.
- Показывать сетевую схему: один телефон с AliceBridge и «Домом с Алисой»,
  колонка и upstream. Различать трафик приложений телефона и клиента хотспота.
  Не предлагать второй телефон как условие настройки или исправление по умолчанию.
- Отчёты об успехе сохранять с точными версиями и достигнутым этапом, а не просто
  флагом «модель работает». OnePlus 15/Shizuku из закрепа — пользовательский отчёт.

Матрица оболочек, форков, разобранных архивов и требований к сетевым проверкам:
[Shizuku: совместимость на 26.10.2026](research/Shizuku-совместимость-2026-10-26.md).
Рекомендация форка зависит от версии Android, SoC и этапа ошибки. Работа Binder,
UserService, TUN и клиентского DNS проверяется отдельно. При смене upstream или
смерти Binder прежние результаты сети становятся недействительными. До реального
клиентского теста нельзя объявлять интернет колонки проверенным.
- Различать сброс настроек, перевод в режим привязки и откат прошивки.
- В терминале явно подписывать устройство и тип доступа. Установка SSH-сервера
  не означает наличие SSH-клиента в shell; дать точную команду для подключения с ПК.
- Карточка пакета показывает способ запуска, а не только кнопку установки.
- Карточка проблемы автоматически включает версии, модель, этап и категорию ошибки.
- BetterYAM исследовать отдельно; наличие ссылки в чате не меняет выбранный YAM автоматически.

## 16. Отказ принятия прошивки и ошибки установки

По дополнительному требованию пользователя: приложение должно объяснять ситуации,
когда колонка не приняла прошивку, а не сводить все проблемы к отсутствию ADB.

Нормальная формулировка: «Колонка не приняла прошивку», если есть соответствующее
доказательство. Не путать с «прошивка не приняла колонку» и не ставить такой диагноз
только по ожиданию, произнесённой общей ошибке или завершению серверной передачи.

| Категория | Необходимое основание | Что показывать и делать |
| --- | --- | --- |
| Скачивание прервано | Обрыв HTTP/Range, неполный набор диапазонов, ошибка транспорта | «Загрузка прервалась»; сохранить прогресс, дождаться докачки/повтора |
| Образ не прошёл проверку на сервере | Несовпадение размера/хеша/CRC, неверная структура | «Файл прошивки повреждён или не прошёл проверку»; не выдавать неполный/непроверенный файл |
| Колонка отклонила образ | Явный код/событие/журнал обновлятора колонки | «Колонка не приняла прошивку»; показать доступную причину без выдуманного объяснения |
| Неподходящая модель/ревизия | Несовпадение подтверждённого устройства и metadata образа | Остановить выдачу/установку; предложить подходящий профиль, не обходить проверку |
| Версия запрещена политикой обновлятора | Явный отказ проверки версии/rollback | Показать конкретный отказ; проверить допустимый переход версий в профиле |
| Подпись или целостность отвергнута колонкой | Явная ошибка проверки обновлятора | Отделить подпись образа от TLS-сертификата сервера; проверить источник/метаданные |
| Не хватает места | Ошибка обновлятора или проверка нужного mount/inode | Показать файловую систему и недостающее место; не удалять пользовательские данные автоматически |
| Ошибка разрешения обновления | Неверный/неоднозначный ответ allow_update, явный отказ API | Диагностировать серверный контракт; не объявлять сам ZIP несовместимым без основания |
| Файл передан, версия осталась прежней | Полная передача плюс свежая версия того же устройства | «Установка не подтверждена: колонка сообщает прежнюю версию»; проверить повторные скачивания и ошибки обновлятора |
| Колонка недоступна после передачи | Исчезновение из сети без версии/boot ID/кода ошибки | «Ждём возвращения колонки; причина пока неизвестна»; перепоиск той же колонки, не автоматический повтор записи |
| Явное TLS-отклонение после передачи | certificate alert от нужного клиента | «Возможно, прошивка не подошла: колонка отклонила сертификат»; не считать установку подтверждённой |

Категория имеет стабильный машинный код и понятный русский текст. Для каждого случая
хранить источник ошибки, ID устройства/сессии, время и степень подтверждённости:
«подтверждено», «предположительно», «причина не установлена».

Если до ADB нельзя получить журнал обновлятора, приложение прямо пишет об этом.
Отсутствие такого доступа не заменяется догадкой. Пользователь может добавить
произнесённую фразу/фотографию экрана как наблюдение, а не как доказанный код ошибки.

Регрессионные сценарии: повреждённый ZIP; несовпадающая модель; отказ подписи;
нехватка места; неправильный allow_update; полная передача без установки; успешная
докачка после обрыва; установка с изменением IP; установка без доступного ADB;
старые события от другой сессии. UI не должен показывать одинаковый диагноз для них.
